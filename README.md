# Домашнее задание «3.2. SQL» — Задача №1 (и опционально №2)

Автотесты на Selenide + JUnit 5 для приложения `app-deadline.jar`, работающего с MySQL.

Проект собран и все описанные ниже сценарии **реально проверены**: `app-deadline.jar`
запускался против настоящей MySQL 8, все REST-запросы (`/api/auth`, `/api/auth/verification`,
`/api/cards`, `/api/transfer`) и все локаторы UI подтверждены вручную перед тем, как
попасть в код тестов.

## 1. Предварительные требования

- Установленный **Docker** и **Docker Compose**.
- **JDK 17** (или новее).
- **IntelliJ IDEA**.
- Установленный **Google Chrome** (Selenide по умолчанию использует Selenium Manager,
  который сам скачает нужный chromedriver под установленный у вас Chrome).

## 2. Как открыть проект в IntelliJ IDEA

1. `File` → `Open` → выберите папку проекта (там, где лежит `build.gradle`).
2. IntelliJ распознает Gradle-проект и предложит импортировать его — соглашайтесь
   (`Trust Project`, затем IDEA сама скачает Gradle wrapper и все зависимости
   из Maven Central — на это нужен интернет и может уйти пара минут при первом запуске).
3. Дождитесь, пока в правом нижнем углу закончится индексация и синхронизация Gradle.

Если IntelliJ не предложил wrapper автоматически: `View` → `Tool Windows` → `Gradle` →
кнопка обновления (двойная стрелка по кругу) в панели Gradle.

## 3. Поднимаем базу данных

Найденный дефект SUT: **при повторном запуске app-deadline.jar падает** с ошибкой
`Duplicate entry 'vasya' for key 'users.login'`, потому что при каждом старте SUT
пытается заново создать демо-пользователей `vasya` и `petya`. Поэтому база данных
должна быть свежей перед КАЖДЫМ запуском SUT.

Специально для этого `docker-compose.yml` не использует именованный volume — данные
живут только внутри контейнера и полностью стираются при пересоздании контейнера.

Откройте терминал в корне проекта и выполните:

```bash
docker compose down -v
docker compose up -d
```

Дождитесь, пока контейнер станет healthy:

```bash
docker compose ps
```

В колонке `STATUS` должно появиться `healthy` (может занять 10–20 секунд).

**Важно:** каждый раз, когда вы хотите перезапустить `app-deadline.jar` (например,
после падения или просто заново), сначала выполните `docker compose down -v && docker compose up -d`
ещё раз — иначе SUT упадёт на старте с той самой ошибкой дублирования.

## 4. Запуск SUT (app-deadline.jar)

В отдельном терминале, из корня проекта:

```bash
java -jar artifacts/app-deadline.jar
```

Параметры подключения к БД указывать не нужно — значения, зашитые в SUT по умолчанию
(`jdbc:mysql://localhost:3306/app`, пользователь `app`, пароль `pass`), совпадают
с тем, что поднимает `docker-compose.yml`.

Дождитесь в консоли строки:

```
Responding at http://0.0.0.0:9999
```

Это значит, что SUT успешно стартовал и слушает порт 9999. Проверить вручную можно,
открыв в браузере `http://localhost:9999` — должна открыться страница логина.

Оставьте это окно терминала открытым на всё время прогона тестов.

## 5. Запуск тестов

### Из IntelliJ IDEA

- Откройте `src/test/java/ru/netology/qa/LoginTest.java`.
- Кликните правой кнопкой мыши по имени класса в редакторе (или по зелёной стрелке
  слева от объявления класса) → `Run 'LoginTest'`.
- Внизу откроется панель с результатами: зелёная галочка у каждого теста — тест прошёл,
  красный крестик — упал, справа будет виден стектрейс с причиной.

### Из терминала

```bash
./gradlew test
```

(на Windows — `gradlew.bat test`)

Если у вас ещё не сгенерирован `gradlew` — просто откройте проект в IntelliJ один раз,
как описано в п. 2, IDE сгенерирует wrapper автоматически. Либо, если у вас установлен
Gradle локально: `gradle wrapper --gradle-version 8.7`.

## 6. Allure-отчёт

После прогона тестов (шаг 5) результаты сохраняются в `build/allure-results/`.
Чтобы посмотреть отчёт:

```bash
./gradlew allureReport
./gradlew allureServe
```

`allureServe` соберёт отчёт и автоматически откроет его в браузере. Если браузер
не открылся сам — терминал выведет локальный URL (обычно `http://localhost:xxxxx`),
откройте его вручную.

Готовый HTML-отчёт без сервера лежит в `build/reports/allure-report/` после
`./gradlew allureReport`.

## 7. Что именно тестируется (Задача №1)

`LoginTest`:

1. **`shouldLoginWithValidCredentialsAndVerificationCode`** — создаёт пользователя
   напрямую в БД через `SqlHelper` (пароль шифруется BCrypt, как это делает сам SUT),
   логинится через форму, достаёт код подтверждения из таблицы `auth_codes` через
   `SqlHelper.getVerificationCode(...)`, вводит его и проверяет, что открылся дашборд.
2. **`shouldShowErrorMessageOnWrongPassword`** — неверный пароль → видно уведомление
   об ошибке.
3. **`knownBug_userIsNotBlockedAfterThreeWrongAttempts`** — см. раздел «Найденные
   дефекты» ниже.

## 8. Задача №2 (необязательная, API)

`api/TransferApiTest`: логин/верификация → токен, получение списка карт, перевод
между двумя картами демо-пользователя `vasya` (баланс проверяется напрямую в БД
через `SqlHelper.getCardBalanceInKopecks(...)`, независимо от ответа API), плюс
тест на найденный баг с переводом на несуществующую карту.

## 9. Найденные дефекты — оформление issue

В ходе ручной проверки (curl-запросы к запущенному SUT) обнаружены два дефекта.
Заведите по каждому issue в вашем GitHub-репозитории со структурой примерно такой:

**Issue 1**

> **Заголовок:** Блокировка пользователя после 3 неверных попыток входа не работает
>
> **Шаги воспроизведения:**
> 1. Запустить SUT, выполнить `POST /api/auth` с неверным паролем 3 (и более) раз подряд для одного и того же логина.
> 2. Выполнить `POST /api/auth` с верным паролем.
>
> **Ожидаемый результат:** после 3-й неверной попытки аккаунт должен блокироваться (ошибка `USER_BLOCKED` / `TOO_MANY_AUTH_REQUESTS`), 4-я попытка (даже с верным паролем) должна быть отклонена.
>
> **Фактический результат:** каждая неверная попытка возвращает `400 AUTH_INVALID`, блокировки не происходит, попытка с верным паролем после этого проходит успешно.
>
> **Компонент:** `app-deadline.jar`, эндпоинт `POST /api/auth`.

**Issue 2**

> **Заголовок:** Перевод на несуществующий номер карты завершается успешно (HTTP 200)
>
> **Шаги воспроизведения:**
> 1. Авторизоваться, получить токен.
> 2. Выполнить `POST /api/transfer` с полем `to`, указывающим на номер карты, которого нет в БД.
>
> **Ожидаемый результат:** ошибка 4xx, деньги не списываются.
>
> **Фактический результат:** `200 OK`, деньги списываются с карты-источника, получатель не проверяется.
>
> **Компонент:** `app-deadline.jar`, эндпоинт `POST /api/transfer`.

## 11. Известные ограничения этого README

Тест перевода (`TransferApiTest.shouldTransferMoneyBetweenOwnCards`) исходит из
того, что баланс каждой из двух карт `vasya` изначально равен 1 000 000 копеек
(10 000 руб.) — это подтверждено вручную на чистой (только что поднятой) БД.
Если вы прогоняете этот тест не на свежей БД (например, повторно, без пересоздания
контейнера MySQL), баланс будет уже другим, и жёсткая проверка `assertEquals`
может не совпасть — в этом случае пересоздайте БД (`docker compose down -v && docker compose up -d`)
и перезапустите SUT перед повторным прогоном тестов.
